z# スタッツ新規登録をチーム単位に変更

## 1. 変更の概要
スタッツ新規登録画面を、ホームチームとアウェイチームのスタッツを1画面でまとめて登録する方式から、指定した1チームのスタッツだけを登録する方式へ変更した。<br>
変更前は、1つのスタッツ登録画面の中でホームチームとアウェイチームの両方を登録していた。<br>
変更後は、URLのteamパラメータによって登録対象のチームを決定し、ホームまたはアウェイのどちらか一方だけを登録する。<br>
新規登録と編集の両方をチーム単位にすることで、画面構成と責務を統一した。<br>


## 2. 変更前の設計
変更前の新規登録画面では、1回の登録処理でホームチームとアウェイチームの両方を扱っていた。<br>

処理の流れ：
```
ホームチームの出場選手を選択
    ↓
ホームチームのスタッツを入力
    ↓
アウェイチームの出場選手を選択
    ↓
アウェイチームのスタッツを入力
    ↓
ホーム・アウェイ両方のスタッツをDBへ登録
```

### 変更前のStatsNewForm
StatsNewFormでは、ホーム用とアウェイ用の状態をそれぞれ管理していた。<br>
```md
管理していた主な状態
- currentHomePlayerIndex
- currentAwayPlayerIndex
- selectedHomePlayerIds
- selectedAwayPlayerIds
<br>
ホーム選手を変更する処理：handleHomePlayerChange<br>
アウェイ選手を変更する処理：handleAwayPlayerChange
```
ステップも4段階だった。
```md
- ステップ1：ホームチームの出場選手を選択
- ステップ2：ホームチームのスタッツを入力
- ステップ3：アウェイチームの出場選手を選択
- ステップ4：アウェイチームのスタッツを入力
```

## 3. 変更理由
新規登録と編集でチーム単位の設計に統一感を持たせるため。

編集画面では、<br>
/games/[gameId]/stats/edit?team=home<br>
または、<br>
/games/[gameId]/stats/edit?team=away<br>
として、ホームまたはアウェイを1チーム単位で編集する設計にした。<br>

新規登録だけホーム・アウェイを一括して扱うと、新規登録と編集で操作単位が異なってしまう。<br>
そのため、新規登録もチーム単位へ変更した。<br>
これにより、
```
新規登録 → 1チーム単位
編集 → 1チーム単位
```
という統一した設計になった。

## 4. 変更後の設計
URLのteamパラメータによって、登録対象のチームを決める。

ホームチームを登録する場合：/games/[gameId]/stats/new?team=home<br>
アウェイチームを登録する場合：/games/[gameId]/stats/new?team=away

### 変更後の流れ
```
指定されたチームを判定
    ↓
指定されたチームの情報を取得
    ↓
そのチームの所属選手だけ取得
    ↓
出場選手を選択
    ↓
選択した選手を1人ずつスタッツ入力
    ↓
登録
    ↓
試合詳細＋スタッツ一覧へ戻る
```

## 5. page.tsxの変更
変更前は、ホームとアウェイの両方のチーム・選手を取得していた。<br>
取得していたデータ：
``` md
- homePlayers
- awayPlayers
- homeTeamName
- awayTeamName
```
また、ホームとアウェイのチームをまとめた、`teams`というデータも使用していた。

変更後はsearchParamsからteamを取得する。
```
team=homeの場合：homeTeamIdを使用してホームの選手を取得する。
team=awayの場合：awayTeamIdを使用してアウェイの選手を取得する。
```
その結果、StatsNewFormへ渡すPropsも変更した。

### 変更前
```
gameId
homeTeamName
homePlayers
awayTeamName
awayPlayers
```

### 変更後
```
gameId
teamName
players
```
page.tsxが登録対象のチームを決定し、StatsNewFormには対象チームの情報だけを渡す。


## 6. searchParamsを使用する理由
[gameId]はURLのパスパラメータとして試合を特定するために使用する。<br>
例：
```
/games/1/stats/new
```
この1がgameIdになる。

一方、teamはクエリパラメータとして、同じ新規登録画面の中で対象チームを切り替えるために使用する。<br>
例：
```
/games/1/stats/new?team=home
/games/1/stats/new?team=away
```
このように、
```
gameId → どの試合か
team → その試合のどちらのチームか
```
をそれぞれ表している。

## 7. teamの入力値を確認する
teamにはhomeまたはawayだけを許可する。<br>
homeでもawayでもない場合は404ページを表示する。<br>

これにより、想定していないURLから不正なチームを指定して登録画面を開くことを防ぐ。<br>
処理の流れ：
```
teamを取得
    ↓
homeまたはawayか確認
    ↓
正しい
    → 処理を続ける

正しくない
    → 404ページを表示
```

## 8. 対象チームを1つに決定する
teamの値に応じて、`teamId`, `teamName`を決定する。

- teamがhomeの場合：`game.homeTeamId`, `game.homeTeam.teamName`
- teamがawayの場合：`game.awayTeamId`, `game.awayTeam.teamName`
を使用する。<br>
その後、決定したteamIdを使って所属選手を取得する。

## 9. 選手取得の変更
- 変更前：ホーム選手とアウェイ選手を両方取得していた。
- 変更後：登録対象チームの選手だけを取得する。

playersという1つの配列にまとめる。<br>
そのため、StatsNewFormはホームかアウェイかを意識する必要がなくなった。

## 10. StatsNewForm.tsxの変更
StatsNewFormでは、ホーム・アウェイそれぞれの状態を管理する必要がなくなった。

### 削除した主な状態
- currentHomePlayerIndex
- currentAwayPlayerIndex
- selectedHomePlayerIds
- selectedAwayPlayerIds

### 追加・統合した状態
- currentPlayerIndex
- selectedPlayerIds

### 削除した主なイベントハンドラー
- handleHomePlayerChange
- handleAwayPlayerChange

### 統合したイベントハンドラー
- handlePlayerChange<br>

これにより、どちらのチームでも同じ処理を使えるようになった。


## 11. StatsNewFormのステップ変更

変更前は4ステップだった。
- ステップ1：ホームの出場選手を選択
- ステップ2：ホームのスタッツを入力
- ステップ3：アウェイの出場選手を選択
- ステップ4：アウェイのスタッツを入力
<br>

変更後は2ステップになった。
- ステップ1：指定チームの出場選手を選択
- ステップ2：指定チームのスタッツを入力
<br>
その後、`登録`でDBへ保存する。

## 12. StatsNewFormの責務
変更後のStatsNewFormは、<br>
渡された1チーム分の選手を対象として、
```
出場選手の選択
    ↓
選手ごとのスタッツ入力
    ↓
登録
```
を管理する。<br>
ホームかアウェイかを判断する処理はpage.tsxに任せている。<br>
そのため、StatsNewFormの責務がシンプルになった。

## 13. PlayerSelect.tsx
PlayerSelect.tsxは変更しなかった。<br>
PlayerSelectは、
```
players
selectedPlayerIds
onChange
```
を受け取って、出場選手の選択を管理している。<br>
ホームかアウェイかという情報を持っていないため、チーム単位の設計変更の影響を受けない。

### PlayerSelectの役割
```
選手一覧を表示
    ↓
チェックボックスで選択
    ↓
selectedPlayerIdsを管理
    ↓
選択したplayerIdを親へ通知
```
どのチームの選手かは親コンポーネントが決定しているため、PlayerSelect自身はチームを意識しない。

## 14. PlayerStatsInput.tsx
PlayerStatsInput.tsxも変更しなかった。<br>
PlayerStatsInputは1人分のスタッツ入力だけを担当している。<br>
`Player`, `PlayerStats`, `onChange`<br>
を受け取ってスタッツを入力する。<br>
ホーム・アウェイの判定処理はないため、チーム単位の設計変更の影響を受けない。

### PlayerStatsInputの役割
```
1人の選手を表示
    ↓
その選手のスタッツを入力
    ↓
変更内容を親へ通知
```

## 15. types.ts
types.tsも変更しなかった。<br>
共通で使用する、<br>
`Player`, `PlayerStats`<br>
の型定義だけを管理している。<br>
ホーム・アウェイに依存した型ではないため、今回の設計変更による変更は不要だった。

## 16. actions.ts
actions.tsも基本的には変更しなかった。<br>
createStatsは、<br>
`gameId`, `playerStats`
を受け取って、statsテーブルへ登録する。<br>

今回、ホーム・アウェイを判断する処理はpage.tsxとStatsNewForm側で行うようにした。<br>
そのため、actions.tsは、**どのチームから来たデータなのか**を知る必要がない。<br>
渡された選手のスタッツをDBへ登録するだけでよい。


### createStatsの処理
```
playerStatsを取得
    ↓
Object.entriesで選手ごとのデータに変換
    ↓
playerIdとgameIdを設定
    ↓
createManyでDBへ登録
    ↓
/games/[gameId]へリダイレクト
```

## 17. コンポーネントの責務
今回の変更によって、各ファイルの責務が明確になった。
- page.tsx：URLを解析し、登録対象チームと選手を決定する
- StatsNewForm.tsx：1チーム分の登録フローを管理する
- PlayerSelect.tsx：出場選手を選択する
- PlayerStatsInput.tsx：1人分のスタッツを入力する
- types.ts：共通の型を定義する
- actions.ts：スタッツをDBへ登録する

## 18. 新規登録と編集の統一
今回の変更によって、新規登録と編集が同じ考え方になった。

### 新規登録
- /games/[gameId]/stats/new?team=home<br>
ホームチームのスタッツを登録
- /games/[gameId]/stats/new?team=away<br>
アウェイチームのスタッツを登録


### 編集
- / games/[gameId]/stats/edit?team=home<br>
ホームチームのスタッツを編集
- /games/[gameId]/stats/edit?team=away<br>
アウェイチームのスタッツを編集

新規登録と編集のどちらも、
- gameId → 試合を指定
- team → チームを指定<br>
という考え方で統一されている。


## 19. 試合詳細画面での最終的な導線
試合詳細＋スタッツ一覧画面では、チームごとの登録状態によって操作を分ける。

スタッツが未登録の場合：
```
[スタッツを登録]
    ↓
/games/[gameId]/stats/new?team=home
または
/games/[gameId]/stats/new?team=away
```

スタッツが登録済みの場合：
```
[スタッツを編集]
    ↓
/games/[gameId]/stats/edit?team=home
または
/games/[gameId]/stats/edit?team=away
```

## 20. 今後の課題
今回の変更で、1チーム単位の新規登録はできるようになった。<br>
ただし、以下は今後対応する。

### 未登録選手の追加
一度スタッツを登録した後に、出場選手として選択し忘れた選手のスタッツを追加できるようにする。<br>
現在の編集画面は、既にstatsレコードが存在する選手を編集する仕組みになっている。

そのため、
```
所属チームにはいる
    ↓
試合のstatsがまだ存在しない
```
という選手を後から追加できる機能が必要。

### 登録済み・未登録の判定
試合詳細画面で、
- スタッツがない → 新規登録ボタン
- スタッツがある → 編集ボタン<br>
と切り替える。

### バリデーション
今回の実装では、バリデーションを後回しにしている。
- 成功数が試行数を超えない
- 数値が0以上
- 出場時間が正しい値

### エラー処理
DB登録時などに発生するエラーを画面上で適切に表示する。


## 21. 学び
今回の変更を通して、画面単位ではなく責務単位でコンポーネントを設計することの重要性を学んだ。<br>
ホームとアウェイをStatsNewFormの中で個別に管理するのではなく、page.tsxで対象チームを決定してから、共通のコンポーネントへ渡すことで処理を共通化できた。<br>
また、URLのパスパラメータとクエリパラメータを使い分けることで、
- gameId → どの試合か
- team → どちらのチームか

という情報を明確に分けることができた。<br>
さらに、新規登録と編集で操作単位を統一することで、画面構成とURL設計を分かりやすくできた。
