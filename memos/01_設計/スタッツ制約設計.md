# 1. 5人制バスケルールに基づく制約候補
## 各スタッツ共通部分
- 0以上である

## シュート関連
- 試行回数 >= 成功回数

## ファウル関連
バスケットボールのルールに基づく退場の条件は次のいずれか
- 個人ファウルは上限5
- テクニカルファウルは上限2
- テクニカルファウルが2回にならなくても、個人ファウルとテクニカルファウルの合計の上限は5

## 試合出場時間
前提として、10分*4クウォーターの試合を想定。
- 選手一人あたりの上限は40分→2400秒
- 1チームの合計は40分*5人分より、12000秒ぴったりでなければならない

# 2. CHECK制約かバリデーションか
CHECK制約に適しているものを検討。<br>
しかしユーザーにもわかるようにCHECK制約をつけてもバリデーションで二重で管理した方が安全といえる。

## 2.1 DB側のCHECK制約にするもの
ここはデータベースに不正な値を入れないため、必ずDB側で保証する方針
| ルール | CHECK制約 | 理由 |
| ---- | ---- | ---- |
| 各スタッツは0以上 | 入れる | 負のスタッツは存在しない |
| 3P成功数 ≤ 3P試投数 | 入れる | 成功数が試投数を超えるのは不正 |
| 2P成功数 ≤ 2P試投数 | 入れる | 同上 |
| FT成功数 ≤ FT試投数 | 入れる | 同上 |
| DQは0または1 | 入れる | フラグなので0/1のみ |
| 出場時間は0以上 | 入れる | 負の時間を防ぐ |
| 出場時間は2400秒以下 | 入れる | 40分を超える値を防ぐ |

## 2.2 DB側に入れてもよいCHECK制約
| ルール | CHECK制約 | 方針 |
| ---- | ---- | ---- |
| ルール | CHECK制約 | 方針 |
| 個人ファウル ≤ 5 | 入れてよい | DBで不正値を防げる |
| テクニカルファウル ≤ 2 | 入れてよい | DBで不正値を防げる |
| 個人ファウル＋テクニカルファウル ≤ 5 | 入れてよい | DBで累積上限を保証できる |
ただし、ここは **「競技ルールに基づく業務ルール」** でもあるので、<br>
DBだけに任せず、最終的には画面側でも同じ条件を検証するとユーザーに分かりやすくなる。

## 2.3 アプリ側のバリデーションにするもの
#### チーム全体の出場時間
```
1チームのplaySec合計 = 12000秒
```
これはDBの通常のCHECK制約には向かない。<br>
理由は、
```
選手Aのstats
選手Bのstats
選手Cのstats
...
```
という複数行を合計して判定する必要があるため。<br>
そのため、
```
DB → 選手1人ごとのplaySecは0～2400秒
アプリ → そのチームのplaySec合計が12000秒か確認
```
と分担する。

# 3. CHECK制約とバリデーションの役割
#### DBの制約
アプリを経由しない登録も含め、不正データを最後に防ぐ

#### アプリのバリデーション
ユーザーに入力ミスを伝える
