# スタッツ編集の複数バリデーションエラー

## 1. エラーメッセージを全件表示する理由
スタッツ編集画面では、複数選手のスタッツを1画面でまとめて編集する。<br>
最初に見つかったエラーだけを表示すると、
```text
エラーを修正
↓
再度保存
↓
別のエラーを確認
↓
再度修正
```
という作業を繰り返すことになる。<br>
そこで、ユーザーが一度の保存操作で修正すべき箇所をすべて確認できるように、<br>
**発生したエラーを全件表示する方法を採用した。**<br>
また、どの選手のエラーなのか分かるように、<br>
エラーメッセージだけではなく、選手ID・背番号・選手名も一緒に管理する。
```ts
type StatsError = {
  playerId: number;
  jerseyNumber: number;
  playerNameKanji: string;
  message: string;
};
```
これにより、
```text
背番号7 田中太郎：3P成功は3P試投以下で入力してください。
背番号15 山田次郎：PFとTFの合計は5以下で入力してください。
```
のように、修正対象を分かりやすく表示できる。

## 2. abortEarlyの概要
Yupの `abortEarly` は、<br>
**バリデーションエラーが発生したときに、最初のエラーで検証を終了するかどうかを指定するオプション**。
```text
true：最初のエラーで検証を終了
false：検証を続け、発生したエラーをすべて取得
```
今回のスタッツ編集では、1選手の中に複数のエラーが発生する可能性があるため、
```tsx
abortEarly: false
```
を指定して、**1選手分のエラーをすべて取得する**ようにした。

## 3. 1選手分のエラー確認から全選手分のエラー確認へ
最初の実装では、1選手分の検証でエラーが発生すると、その時点で処理を終了する形だった。<br>
しかし、編集画面では複数選手のスタッツをまとめて編集するため、<br>
1人のエラーだけで処理を止めると、他の選手のエラーを確認できない。<br>
そこで、`for...of` を使って**全選手を1人ずつ検証し、エラーが発生しても次の選手の検証を続ける**ようにした。
```tsx
for (const { playerId, stats } of statsData) {
  try {
    await playerStatsSchema.validate(stats, {
      abortEarly: false,
    });
  } catch (error) {
    // エラーを取得
  }
}
```
この処理によって、
```text
選手Aを検証 → エラーを取得
選手Bを検証 → エラーを取得
選手Cを検証 → エラーを取得
```
というように、**全選手のエラーを収集できる**ようになった。

## 4. 今回のバリデーションの考え方
今回の実装では、2段階でエラーをすべて取得する。
```text
1選手分のスタッツ
↓
abortEarly: false
↓
その選手の複数エラーを取得
```
さらに、
```text
選手A
↓
選手B
↓
選手C
```
と全選手を検証することで、<br>
**「1選手内の複数エラー」と「複数選手のエラー」の両方をまとめて表示できるようにした。**<br>
画面の構成に合わせて、ユーザーが一度に修正箇所を把握できるバリデーション結果の表示方法を採用した。

## 5. 「変更を保存」からDB更新までの処理順
スタッツ編集画面では、「変更を保存」ボタンをクリックすると、以下の順番で処理する。
```text
[変更を保存]
↓
handleSubmit()を実行
↓
編集したスタッツをDBへ渡す形式に変換
↓
全選手を1人ずつYupで検証
↓
1選手分の検証ではabortEarly: falseを指定
↓
エラーがあればerrors配列へ追加
↓
全選手の検証が完了
↓
エラーが1件以上ある？
    ↓ YES
    statsErrorsへ保存
    ↓
    画面上部にすべてのエラーを表示
    ↓
    DB更新は実行しない

    ↓ NO
    statsErrorsをクリア
    ↓
    updateStats()を実行
    ↓
    Server ActionでDBを更新
    ↓
    試合詳細・スタッツ一覧画面へ戻る
```
コード上では、
```tsx
const statsData = editStats.map(({ playerId, player, ...stats }) => ({
  playerId,
  stats,
}));
```
でDB更新用のデータに変換する。<br>
その後、
```tsx
for (const { playerId, stats } of statsData) {
  try {
    await playerStatsSchema.validate(stats, {
      abortEarly: false,
    });
  } catch (error) {
    // エラーを収集
  }
}
```
ですべての選手を検証する。<br>
エラーがある場合は、
```tsx
if (errors.length > 0) {
  setStatsErrors(errors);
  return;
}
```
として、**`updateStats()` を実行せずに処理を終了する。**<br>
すべての検証に成功した場合のみ、
```tsx
await updateStats(gameId, statsData);
```
を実行してDBを更新する。

このように、<br>
**「検証 → エラー表示」または「検証成功 → DB更新」**という順番で処理することで、<br>
不正なスタッツがDBへ保存されることを防いでいる。
