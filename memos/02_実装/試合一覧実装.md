# 試合一覧

## スコア列のデータをどのように表示させるか

### 完成系のイメージ
```
(形式)
[ホームチーム名] 得点 - 得点 [アウェイチーム名]

(例)
湘北高校　86 - 87 陵南高校
```

---

### 1. 必要なデータを取得
includeを用いて関連するもののうち必要なものを取得する
``` tsx
// Prismaを使ってGamesテーブルから全件取得
const games = await prisma.games.findMany({
  orderBy: {
    gameId: "desc", // 試合IDの降順
  },
  // include：関連するテーブルを一緒に取得する
  include: {
    /* Gamesに紐づいているhomeTeam/awayTeamも取得する */
    homeTeam: true,
    awayTeam: true,
    /* Gamesに紐づくStatsも取得する */
    stats: {
      // include：関連するテーブルを一緒に取得する
      include: {
        /* 各Statsに紐づくplayerも取得する */
        player: true,
      },
    },
  },
});
```
```
取得できるデータ
Games
├── homeTeam
├── awayTeam
└── stats
    └── player
```


### 2. ホームチーム名とアウェイチーム名の表示
gamesは複数の試合が入った配列なので、map()の中で1試合ずつ処理する。
- ホームチーム名
``` tsx
{games.map((g) => {
  g.homeTeam.teamName
}}
```
- アウェイチーム名
``` tsx
{games.map((g) => {
  g.awayTeam.teamName
}}
```
実際の試合一覧では、map() の中で1試合分の <tr> を作成し、その中でチーム名を表示する。

### 3. 各チームの得点計算 【見直し前の実装案】
#### 使用するメソッド
- .filter() <br>
条件に合致するすべての要素を新しい配列に抽出する<br>
``` ts
{games.map((g) => {
  const homeSumP3M = g.stats
    .filter((stat) => stat.player.teamId === g.homeTeamId)
})}
```
この場合、<br>
stat.player.teamId → そのStatsを記録した選手の所属チームID<br>
g.homeTeamId → その試合のホームチームID<br>
を比較し、一致するStatsだけを抽出している。

- .reduce() <br>
配列を1つの値にまとめる<br>
``` 
基本的な形
reduce((累積値, 現在の要素) => 何かしらの処理, 累積値の初期値)
```
例えばホームチームの3P得点を計算する場合：
``` tsx
{games.map((g) => {
  const homeSumP3M = g.stats
    .filter((stat) => stat.player.teamId === g.homeTeamId)
    /* 累積値の初期値は0、
       現在のStatsの3P成功数を3倍し、累積値に加える */
    .reduce((sum, stat) => sum + stat.p3M * 3, 0)
})}
```
この処理では、<br>
sum → これまでに計算した3P得点の累積値<br>
stat → 現在処理しているStats<br>
0 → 累積値の初期値<br>
となる。

## テーブル設計の見直し
### 現在の設計におけるデメリット
上記「スコア列のデータをどのように表示させるか」について考えている過程で以下の問題に気づいた。

- 試合一覧でスコアを表示するために、Games → Stats → Players と関連データをたどる必要がある
- ホームチーム・アウェイチームを判定するために、Statsに紐づく選手の所属チームを確認する必要がある
- 3P・2P・FTの成功数をそれぞれ集計し、最終スコアを計算する必要がある
- 試合一覧画面を表示するだけでも、複数のデータ取得・抽出・集計処理が必要になる
- 今後データ量が増えた場合、これらの処理による負荷が大きくなる可能性がある<br>

そのため、試合一覧画面で最終スコアを表示するだけなら、試合テーブルに最終スコアを直接持たせるほうがシンプルではないかと考えた。

### 試合テーブル設計ver.2
そこで、試合テーブルの設計を見直すことにした。

| カラム物理名 | データ型 | 制約 | 論理名 |
| :----: | :----: | :---- | :----: |
| game_id | SERIAL | PRIMARY KEY | 試合ID |
| tipoff_time | TIMESTAMP | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 試合開始日時 |
| home_team_id | INTEGER | NOT NULL, FK->teams.team_id | ホームチームID |
| away_team_id | INTEGER | NOT NULL, FK->teams.team_id | アウェイチームID |
| home_score | INTEGER | NOT NULL, DEFAULT 0 | ホーム最終スコア|
| away_score | INTEGER | NOT NULL, DEFAULT 0 | アウェイ最終スコア|

#### ver.2の設計のメリット(◎)・デメリット(△)
- （◎）試合一覧画面でスコアを表示するための集計処理を省略できる
- （◎）試合一覧では homeScore と awayScore を取得するだけでスコアを表示できる
- （◎）試合テーブルだけで「その試合の最終結果」を確認できる
- （△）Statsテーブルから計算した得点と、Gamesテーブルに保存されている得点の整合性をどのように保つかという問題が発生する<br>

現時点では、まず各画面の基本機能を完成させることを優先する。<br>
<br>
そのため、Statsから計算した得点とGamesに保存されている得点の整合性については、いったん後回しにする。<br>
<br>
今後、スタッツ登録・編集機能を実装した後に、必要であればGamesのスコアを自動更新するなど、整合性を保つ方法を検討する。
